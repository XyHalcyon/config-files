# 技术文档行文风格规范

> 来源：算子开发全流程指南（流程型长文）与赋能技术集（案例型文档：CPP 混合序列优化技术、KV Cache 池化技术）的写作实践总结。写技术文档时默认执行。

## 一、文档骨架

| 文档类型 | 骨架 |
|---|---|
| 案例型（赋能技术集） | 一、业务背景 → 二、技术挑战 → 三、技术原理 → 四、现场实施过程 → 五、实践效果与价值 |
| 流程型（全流程指南） | 背景/软件栈 → 交付标准 → 全流程 → 各阶段详解（设计→实现→验证→接入）→ 收益与清单 → 案例实录 |

## 二、各部分写法

| 部分 | 写法 |
|---|---|
| 业务背景 | 直入业务事实与量化痛点（长度跨度、显存上限、时延数字），不铺垫 |
| 技术挑战 | 加粗要点列表，每条"问题名：现象 + 后果" |
| 技术原理 | 按机制/角色/层次拆解，配架构图与对照表 |
| 现场实施 | 编号步骤 + 版本信息 + 真实可执行的参考配置代码块；现网问题用"现象/根因/处置"三列表 |
| 实践效果 | 实测数据对照表（优化前/后/变化，注明测试口径）+ 客户价值要点列表 |
| 案例实录 | 前文模板的实例化，与前文章节一一呼应，应用不复述机制 |

## 三、句式规则

- 直述事实，不设问自答。❌"问题来了：怎么保证 H_res 双随机？" ✅"难点在于保证 H_res 双随机。"；❌"怎么证明算得对？" ✅"证明算得对，用的是双标杆比值法。"
- 不用比喻、拟人、修辞性强调。❌掐表、两条路、新路、"定理告诉我们"、"那个反差" ✅计时、两种做法、"Birkhoff-von Neumann 定理："、"…的差异"
- 不用说教与自定规矩框架（注意、务必、必须说清楚、硬性规定、纪律、关卡、四条要求），警告式断语改为陈述事实。❌"不测就是隐患" ✅"这条分支真实训练不常走，也纳入用例"
- 无自指。❌本文、本章节、以……为例说明 ✅删除或改为"以……的开发为例："
- 不做章节间跳转。❌见 X.Y、详见 X.X、参见某章节、（见下）、分见 X.X、X.X ✅把关键约束直接写进当前位置（"对齐规则详见 3.4"→"须按 2MB（host_*）或 1GB（device_*）对齐"），或陈述结构事实（"协议、容量各有专题小节"）；指向外部仓库与官方文档的"参考"保留
- 压缩口语展开。收敛成→整理成；进 step→折算到训练 step；判污染→判定为受污染；精度过了轮到性能→精度通过，接下来测性能
- 术语首次出现给定义或括注（TTFT、PD 分离、GVA）；专有名词、代码、命令保留原文
- 同一概念全文一个叫法：wall=实际耗时、busy=设备执行时间、阈值不混用"门槛"
- 形象表述仅限给机制定性命名（"空间换时间""指纹"），不进入过程叙述

## 四、数字与判据

- 数字带单位与量级：约 5 秒、~110 GB/s、50GB×8 卡=单机 400GB
- 判据写明阈值与来源：bf16 ≤ 5e-3、95% 置信区间下限不超阈值、MERE < 阈值且 MARE < 10×阈值
- 对比固定口径：同资源、同流量分布、同统计口径；口径不同不能同表比较（"算子本身"口径与 step 口径分开给）

## 五、图表规则

- 表格用于对比与数据，代码块给可执行命令/配置
- 每图一句 alt 说明；改正文必同步改图，图中术语与文字严格一致
- SVG 是 XML 文本可直接编辑；图内文字宽度按"中文≈字号 px/字"估算，改字先估宽
- 删图后核对引用完整性；删小节后重编号保持连续

## 六、术语判断标准与替换映射

### 判断标准（先判断语境，再决定替换）

一个词是不是"黑话"取决于语境和读者，不取决于词本身：

- **领域标准术语 → 保留**："五元组"在网络/安全领域（源 IP、目的 IP、源端口、目的端口、协议）是标准术语；"UT/ST"是电信测试流程的标准阶段名；"墙钟时间"是 HPC 文献的通行译法。面向该领域读者直接用；读者可能跨界时，首次出现加一句括注即可。
- **自造压缩语 / 自定分级 → 展开或删除**："A 类/B 类证据"这类自造分类（同"四条要求"）没有外部出处，展开成"实测证据 / 手算估算"，或删掉整个框架。
- **中英混压缩 → 正文展开、代码保留**："发射 / alloc"在正文里写全（kernel 提交、内存分配）；代码与命令里的标识符不动。
- **选定叫法后全文统一**：wall 统一叫"实际耗时"就不再出现"墙钟"；阈值与门槛二选一。

判断三问：目标读者的领域里这是不是标准叫法？首次出现能否无歧义理解？全文是否只用这一个叫法？

### 替换映射（记录当时语境，非普适禁令）

| 原词 | 当时替换为 | 语境说明 |
|---|---|---|
| 对拍 | 输出比对 | 算子交付文档面向通用读者；算法竞赛文档里"对拍"是标准词，正当 |
| 五元组 | 五项输出 | 当时指"五个待比输出"，属该文自造用法；网络/安全领域的五元组是标准术语，不能禁 |
| 读数 | 结果 | 仪器/计量语境（传感器读数）正当；当时泛指测量结果，故替换 |
| 发射 / alloc | kernel 提交 / 内存分配 | 正文压缩语展开；代码标识符保留原文 |
| bound（裸用） | 瓶颈判定 | Memory-bound / Compute-bound 是 Roofline 标准术语，保留作括注；只替换无修饰的裸用 |
| A 类 / B 类证据 | 实测证据 / 手算估算 | 自造分级，无外部出处 |
| UT/ST | 单元测试、系统测试 | 电信测试流程标准阶段名；面向流程内读者可保留 |
| 墙钟 | 实际耗时 | "墙钟时间"是 HPC 通行译法；该文档选"实际耗时"并统一 |
| snake name | snake_case 名 | snake_case 是标准写法，"snake name"不是 |
| D2D staging | D2D 中转拷贝 | staging 在数据工程（暂存区）是标准词；"D2D staging"压缩后不自明 |

### 明确保留的正例

- 领域标准词：Memory-bound / Compute-bound（Roofline）、五元组（网络）、墙钟时间（HPC）、UT/ST（测试流程）
- 专有名词与工具名：Golden、ATK、mspti、Roofline、aclnn、DFunction
- 明确决定保留的惯用语：冒烟（smoke test 通行译法）、JIT（首次出现可加注"（即时编译）"）

## 七、复杂度与去重原则

- 不发明实际开发中不存在的流程概念；维度宁少勿多（六维测试→四个方面）
- 一个概念在一处讲透，其他位置只引用结论；案例章是模板的实例化，不复述机制
- 图文同源：正文怎么改，图就怎么改，改完 grep 验证无残留
